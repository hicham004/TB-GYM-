## Slice 1 (plan row R5.4a): the player logs what the coach prescribed

Web only. One session. The most valuable fix in this review: it protects everything P1 to P4 built.

**Build**

1. **Prescribed numbers first (D1).** In `src/web/src/app/features/training/workout-set-drafts.ts`
   (`draftFromSet`, about line 192), the draft takes last time's load and reps before the prescription:
   `set.actualLoad ?? matchingPrevious?.load ?? set.prescribedLoad`. Live, Maya's Back Squat target was
   52.5 kg × 5, the row pre-filled 50 × 5 (set 3: 50 × 7) and ✓ logged "50 kg × 5" under a Target line
   saying 52.5 kg. Change the order to prescription first, last time only when the set has no prescribed
   load or reps, and keep the "Last time" line and the Previous column as reference. Record the rule in
   `docs/DOMAIN-RULES.md` section 4 as a TRN line ("a set's draft starts from the prescription; last
   time's numbers are a reference and the fallback when nothing is prescribed"). The plan's M2 text says
   both "pre-filled with the target and last time's numbers" and "one tap logs a set as prescribed";
   the second sentence is the rule. Decision for the owner: none needed unless they want last time's
   numbers to win, in which case the plan's M2 sentence changes instead.
2. **Rest is over (U6).** `src/web/src/app/features/training/today-training.html` line 540 removes the
   timer at zero and nothing else happens. Add `navigator.vibrate` where it already exists for a PR, a
   polite live region "Rest is over", and an optional short beep, all respecting reduced motion and the
   phone's silent switch (a beep is best effort). Everfit alerts when rest ends; Hevy Coach sends a
   notification (links at the end).
3. **No native selects in the player (U7).** The unit choice (line 157), the workout picker (line 114)
   and the swap picker (line 423) are browser `<select>`s, which plan §2 rule 8 forbids. Use the kit's
   segmented control for kg/lb, and the kit menu for the workout and the swap. The swap is a write
   (`substitute`), so keep its confirmation and busy state.
4. **Nothing under the tab bar (D8).** The client tab bar renders inside the player (the plan's own
   fidelity gap). An automation click on "Finish workout" at phone height landed on the Progress tab,
   so the button sat under the bar. Hide the tab bar while the player is open (the prototype has none
   there), or give the player a scroll padding equal to the bar plus the rest timer. Check by hand on a
   phone before calling it done. WCAG 2.2 2.4.11 is the relevant rule (link at the end).

**Not in this slice:** GSAP moments, the set table with a "previous" column from the prototype, the
pill tools, the saved kg/lb reaching the player (TRN-016, owner decision in the plan's follow-ups).

**Done when:** plan §2; `workout-set-drafts.spec.ts` covers the precedence (prescribed, then last time,
then nothing); Vitest for the rest end and the three controls; the player's Playwright spec updated;
`today-training.scss` stays under its 8 kB error line (it is at 8.00 kB); the TRN line written.

## Slice 2 (plan row R5.4b): one client, one mode, and honest failures

Web only. One session. Low risk.

**Build**

1. **Client pages in both modes (D3).** Live, a client in dark mode flips between light and dark pages:
   `main[data-mode="light"]` on `/training/program` and `/checkins/me`, dark on `/progress/dashboard`,
   `/nutrition/today`, `/messages`, `/me`, `/notifications`. Routes without `REDESIGNED`:
   `src/web/src/app/features/training/training.routes.ts` lines 34 to 44 (`program`, `today`),
   `src/web/src/app/features/checkins/checkins.routes.ts` lines 31 to 42 (`me`, `me/:assignmentId`), and
   `/` is `REDESIGNED_FOR_STAFF` in `src/web/src/app/app.routes.ts` line 40, so the client's Today stays
   light. Do one dark screenshot pass for client Today, Training, Check-ins (list and flow) and the
   player (always dark; it carries `data-mode="dark"` since R5.3e), fix what the pass finds, then mark
   the routes. This closes the plan's "Client dark mode" follow-up.
2. **A client who isn't yours (D4).** A coach opening another coach's client gets "The client profile
   could not be loaded." and a Retry that can never succeed; the server answered 404 twice.
   `src/web/src/app/features/clients/client-workspace.context.ts` line 68 words every failure the same.
   Map 404 to a "This client isn't here" state with a link to Clients, as the check-in review does
   ("This check-in isn't here", `client-checkin-review.html`). Keep Retry for real failures.
3. **A page that won't open (D5).** Offline, a sidebar click did nothing: the console showed "Failed to
   fetch dynamically imported module" and the person stayed where they were. The same happens after a
   deploy with new chunk hashes, which is the common case for an installed app in a gym. Register a
   router navigation error handler (`withNavigationErrorHandler`) that shows the kit toast "That page
   couldn't be opened. Check your connection and try again", and offers Reload when the error is a
   chunk load after a deploy. Keep the exit guards' own refusals out of it (a cancelled navigation is
   not an error).

**Not in this slice:** the live-message read rule (ADR 0020, owner decision), the backend words in
notices, a service worker or offline cache (the plan rules them out).

**Done when:** plan §2; `theme.e2e.ts` covers the three client routes in dark; Vitest for the 404
state and the navigation error toast; screenshots at 390 px in dark for the owner.

## What the competitors do (documented behaviour, with links)

- **Everfit.** A client checks sets off one by one; with auto-rest on, a timer pops up on the check-off
  and "you'll receive an alert when rest ends"; swipe to save; then a difficulty rating and a comment
  thread, and the coach's notification opens the completed workout with the thread.
  https://help.everfit.io/en/articles/5829094-client-app-track-a-workout and
  https://help.everfit.io/en/articles/4346734-comments-for-completed-workouts. The coach dashboard sorts
  clients into At Risk, Need Attention and On Track from thresholds the coach sets:
  https://help.everfit.io/en/articles/15999847-configure-your-check-in-dashboard. TB Gym's fixed
  CLI-018 rules are enough for founding coaches; the rest-end alert and prescribed-first logging are the
  gaps (slice 1).
- **TrueCoach.** Compliance is exercises completed over exercises assigned for 7, 30 and 90 days; a 20%
  drop in any window flags Needs Attention; clients never see it:
  https://help.truecoach.co/en/articles/2403738-compliance-rates. TB Gym shows the last 7 days only; a
  4-week adherence line on the client Overview would be a cheap later addition.
- **Hevy Coach.** The dashboard counts clients active and inactive in the last 7 days and lists latest
  activities with the workout's name, duration, volume and sets:
  https://help.hevycoach.com/en/articles/8460727-dashboard. The client app pre-fills the program's
  variables and notifies when rest ends: https://hevycoach.com/features/client-app/ (a marketing page).
  TB Gym's feed is comparable. Inferred, not documented: Hevy opens the workout from the feed, TB Gym
  opens the client's Training tab, one tap short of the session.
- **ABC Trainerize.** Its help centre blocked fetching, so this is from search summaries only, not read
  in full: clients open a scheduled workout and tap Track; rest timers start from the rest step; the
  Progression Spreadsheet edits targets per scheduled day across weeks.
  https://help.trainerize.com/hc/en-us/articles/208689026 and
  https://help.trainerize.com/hc/en-us/articles/212130826. TB Gym's preview-first progression (P1 to
  P4) covers the same ground with an explanation per set.

## Running the review stack again

Without touching `bin/`, other sessions' processes or the development database: build the API and the
Worker into a scratch folder (`dotnet build src/backend/TB.Gym.Api/TB.Gym.Api.csproj -c Release -o
<scratch>/api`, the same for `TB.Gym.Worker`), run `dotnet TB.Gym.Api.dll demo-workspace` from that
folder with `ASPNETCORE_ENVIRONMENT=Development`, `Seed__Enabled=false`,
`Database__ApplyMigrationsOnStartup=true` and `ConnectionStrings__Database` naming a new database on the
native PostgreSQL (about 8 minutes; it prints one line per demo week), then start the API with
`ASPNETCORE_URLS` on a spare port and `Application__PublicBaseUrl` set to the `ng serve` origin, the
Worker with the same connection string, and `ng serve --port <spare> --proxy-config <scratch>/proxy.json`
with the repo's `.tools/node`. Sign-ins are in the plan (§7). Drop the database `WITH (FORCE)` and stop
only your own processes when done.
